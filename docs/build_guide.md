## Stage 0: Get your ServiceNow sandbox

**Time:** 15 minutes, plus waiting time

**Goal:** Get a free personal ServiceNow instance on the Zurich release. Everything else in this project is built inside it.

**Why it matters:** A PDI is a free sandbox from ServiceNow. Nothing we do in it can touch company systems.

**Before you start**

- Choose the sandbox owner. Each developer account can have one instance, and the owner must sign in to the Developer Site at least once a week.
- Have a password manager ready. The admin password goes there and nowhere else.

### Step 0.1: Sign in to the ServiceNow Developer Site

*Where:* Developer Site

1. Open the Developer Site with the button below.
2. Click **Sign In**. No account yet? Click **Sign Up**, fill in the form and confirm the email you receive.

- Open the Developer Site: <https://developer.servicenow.com>

**You should see:** You are signed in. Your name or picture shows at the top right.

**If not:**

- The site shows an error or says it is busy: wait a few minutes and reload. The site had outages in 2026.

### Step 0.2: Check whether you already have an instance

*Where:* Developer Site

1. Open your profile menu (top right) and look for **Manage my instance**, or look at the home page.
2. If an instance is listed, note its release. If it is Zurich, go straight to step 0.5.
3. If it is another release and nothing in it matters to you, release it with **Release instance**. Releasing deletes everything in it.

**You should see:** You know whether you already have an instance, and on which release.

### Step 0.3: Request a Zurich instance

*Where:* Developer Site

1. Click **Request Instance**.
2. Choose **Zurich** in the list of releases. Do not choose Australia (the current release) or Brazil (the newest, still in early access).
3. Click **Request**.

**You should see:** A message that your instance is being prepared (usually a few minutes), or that you are on a waitlist.

**If not:**

- "We were unable to assign an instance to you": sign out, go back to the Developer Site home page, sign in and try again.
- On a waitlist: stay on it. Leaving and joining again puts you at the end. Waits of several days were common in 2026.
- Zurich is not in the list: read **Zurich is not offered** under Troubleshooting below.

**Write down:** Release requested, and on which date

### Step 0.4: While you wait: learn and prepare (optional)

*Where:* This guide

1. Read **Basics** in this guide (five minutes) and files 01 to 05 in the repository's docs folder.
2. Open **Northstar files** to see the invented company we will build.
3. Come back when the email says your instance is ready.

**You should see:** You can explain the five stories in your own words.

### Step 0.5: Save the instance details

*Where:* Developer Site

1. When the instance is ready, the Developer Site shows its address (like https://dev123456.service-now.com), the user name **admin** and a password.
2. Put the password in your password manager. Never type it into this guide, a chat or the repository.
3. Type the instance address below. The guide uses it to open the right ServiceNow pages for you.

**You should see:** The address is saved, and the green Open buttons in later steps work.

**Write down:** Instance address, Sandbox owner (initials)

**Screenshot:** `evidence/S0_01_developer_site_instance.png`

### Step 0.6: Sign in and check that it is Zurich

*Where:* Your instance

1. Click **Open stats page** and sign in as **admin** with the password from your password manager.
2. Find the line **Build name**.

- Open stats page: open `stats.do` on your instance

**You should see:** **Build name: Zurich**

**If not:**

- Another release: stop here. Release the instance and request Zurich, or follow **Zurich is not offered** under Troubleshooting.
- The page says the instance is asleep: wake it on the Developer Site. Waking takes 3 to 5 minutes, at most 20.

**Write down:** Build name, Build tag (optional)

**Screenshot:** `evidence/S0_02_build_name_zurich.png`

### Step 0.7: Set the weekly reminder

*Where:* Calendar

1. Create a weekly calendar reminder for the sandbox owner: **Sign in to developer.servicenow.com**.
2. The Developer Site deletes an instance that nobody used for 10 days. Signing in also wakes a sleeping instance.

- Reminder text: `Sign in to developer.servicenow.com (keeps the SAM sandbox alive)`

**You should see:** The reminder is in the owner's calendar.

### Checks before you finish the stage

- [ ] You can sign in to the instance as admin.
- [ ] The stats page shows Build name Zurich, or the release rule was applied and written in tracker/decisions.md.
- [ ] The admin password is only in a password manager.

### If something goes wrong

| Problem | What to do |
| --- | --- |
| Zurich is not offered | Join the Zurich waitlist once and wait up to 7 days. If no Zurich instance arrives, request Australia, write the decision in tracker/decisions.md and carry on. Never call an Australia instance Zurich. |
| The instance is asleep | Sign in to the Developer Site and use the wake button. It takes 3 to 5 minutes, at most 20. |
| Forgot the admin password | Developer Site, profile menu, Manage instance password. The label can differ slightly. |
| Still on the waitlist after many days | Keep your place. ServiceNow support does not handle PDIs. Use the time for the reading in step 0.4. |


## Stage 1: Switch on SAM Professional

**Time:** 2 to 3 hours (the installation runs by itself for 1 to 2 hours)

**Goal:** Install Software Asset Management Professional with its sample data, check every part, open the Software Asset Workspace and write down how things look before we add our data.

**Why it matters:** SAM Professional is a paid product. On a sandbox it can be switched on for free from the Developer Site. Checking each part now saves hours later.

**Before you start**

- Stage 0 is finished: you can sign in to the Zurich instance.
- The instance is awake: open it once before you start.

### Step 1.1: Start the change log for this stage

*Where:* Your instance

1. Open **Update sets** below and click **New**.
2. Name it **SAM Portfolio S1 Foundation** and click **Submit**.
3. Open it again and click **Make This My Current Set**.

- Update set name: `SAM Portfolio S1 Foundation`

- Update sets: open `sys_update_set_list.do` on your instance

> An update set records our configuration changes so we can export them as a backup in Stage 6. Every stage gets its own.

**You should see:** **SAM Portfolio S1 Foundation** shows State **In progress** and is your current update set.

**If not:**

- To always see the current update set: profile picture (top right), **Preferences**, **Developer**, switch on the update set picker.

### Step 1.2: Start the SAM Professional installation

*Where:* Developer Site

1. On the Developer Site open your profile menu (top right) and choose **Activate Plugin**. On some versions it sits on the **Manage my instance** page.
2. Search for **Software Asset Management Professional**.
3. Click **Activate** and choose the option **with demo data**. Confirm.
4. Click **Start timer**. Do not change anything in the instance while it installs.

- Search text: `Software Asset Management Professional`

- Open the Developer Site: <https://developer.servicenow.com>

**You should see:** A message that the activation has started. Later the Developer Site shows it as complete.

**If not:**

- It failed: try once more. Failed again: use **Activation keeps failing** under Troubleshooting.
- Only an option without demo data: use it. Our own data arrives in Stage 2.
- Not in the list: search for **Software Asset** and write down what you see.

**Write down:** Activation attempts, times and any error text

**Waiting time:** 1 to 2 hours

### Step 1.3: While it installs: read the basics (optional)

*Where:* This guide

**You should see:** You can explain installation, entitlement and reconciliation in one sentence each.

## Stage 2: Create our fake company, Northstar

**Time:** 45 to 60 minutes

**Goal:** Load Northstar Manufacturing into the sandbox: 60 employees, 45 laptops, 12 servers and 248 software installations. The five license stories are built on this data.

**Why it matters:** In a real company this data comes from scanning tools on every computer. In the sandbox one script plays that tool and creates the same records a scan would. All of it is synthetic data.

**Before you start**

- Stage 1 is finished: SAM Professional is active and the workspace opens (or the fallback is noted).

### Step 2.1: Start the change log for this stage

*Where:* Your instance

1. Open **Update sets** below, click **New**.
2. Name it **SAM Portfolio S2 Data** and click **Submit**.
3. Open it again and click **Make This My Current Set**.

- Update set name: `SAM Portfolio S2 Data`

- Update sets: open `sys_update_set_list.do?sysparm_query=nameSTARTSWITHSAM%20Portfolio` on your instance

**You should see:** **SAM Portfolio S2 Data** is your current update set.

### Step 2.2: Open Scripts - Background

*Where:* Your instance

1. Click **Scripts - Background**.
2. If a message says you need elevated rights: profile picture (top right), **Elevate role**, tick **security_admin**, click **Update**, then open Scripts - Background again.

- Scripts - Background: open `sys.scripts.do` on your instance

> A background script runs once, as admin. Our scripts only create or update Northstar records.

**You should see:** A page with a large text box and a **Run script** button.

### Step 2.3: Run the Northstar loader

*Where:* Your instance

1. Click **Copy script**.
2. Click into the big text box in Scripts - Background and paste (Ctrl+V, or Cmd+V on a Mac).
3. Keep the scope **global** if asked, then click **Run script**.
4. Wait for the result page, about 1 to 2 minutes. Copy its lines into the box below.

Script: `data/northstar/servicenow/01_load_northstar.js` (copy it from the app or open the file).

**You should see:** The result ends with **RESULT: OK** and shows 60 users, 45 computers, 12 servers and 248 installations, each with a discovery model.

**If not:**

- The result says CHECK or ERROR: paste the lines into the box and read the notes. Running the script again fixes most issues.
- Ran it twice by mistake: no problem. The script updates records instead of duplicating them.
- Nothing happens for a long time: wait 5 minutes, then check the installations list in step 2.6. The records may already be there.

**Write down:** Result lines from the script

**Screenshot:** `evidence/S2_01_loader_result.png`

### Step 2.4: Check the people and computers

*Where:* Your instance

1. Open the three lists.

- Northstar users: open `sys_user_list.do?sysparm_query=company.name%3DNorthstar%20Manufacturing` on your instance
- Northstar laptops: open `cmdb_ci_computer_list.do?sysparm_query=nameSTARTSWITHNSM-WS` on your instance
- Northstar servers: open `cmdb_ci_server_list.do?sysparm_query=nameSTARTSWITHNSM-` on your instance

**You should see:** 60 users, 45 laptops and 12 servers.

**Screenshot:** `evidence/S2_02_people_and_computers.png`

### Step 2.5: Check the server processor numbers

*Where:* Your instance

1. Open **Northstar servers** and click **NSM-SQL-01**.
2. Find **CPU count** and **CPU core count**.

- Northstar servers: open `cmdb_ci_server_list.do?sysparm_query=nameSTARTSWITHNSM-` on your instance

> CPU core count means cores per processor. Per core licensing in Stage 4 is calculated from these two numbers.

**You should see:** NSM-SQL-01: **CPU count 2**, **CPU core count 4**, so 8 cores. NSM-WIN-01 shows 2 and 8, so 16 cores.

### Step 2.6: Check the software installations

*Where:* Your instance

1. Open **Northstar installations** and check the row count.
2. Click an **Adobe Acrobat (64-bit)** row on **NSM-WS-001** and look at the field **Discovery model**.

- Northstar installations: open `cmdb_sam_sw_install_list.do?sysparm_query=installed_on.nameSTARTSWITHNSM-` on your instance

> Each row is one installation: one program on one computer.

**You should see:** 248 installations. The Discovery model field is filled in.

**If not:**

- Discovery model is empty: wait one minute and reload. Still empty: type **sys_script.list** in the All menu search, find the business rule **Create a Software Normalization** and check that it is active.

**Screenshot:** `evidence/S2_03_installations.png`

### Step 2.7: Group the installations by discovery model

*Where:* Your instance

1. In the installations list, right-click the column heading **Discovery model** and choose **Group By Discovery model**.

> Each group is one discovery model: one record per unique publisher, name and version found on computers.

**You should see:** 8 groups: 5 licensed products (Acrobat, SQL Server, Visio, Project, Windows Server) and 3 free tools (Chrome, 7-Zip, Notepad++).

**Screenshot:** `evidence/S2_04_installations_by_discovery_model.png`

### Step 2.8: Run the name cleaning once

*Where:* Your instance

1. Open **Normalization jobs**. Open the job that normalizes discovery models. Its name looks like **SAM - Normalize discovery models using content library rules**.
2. Click **Execute Now** and wait 2 to 5 minutes.

- Normalization jobs: open `sysauto_list.do?sysparm_query=nameLIKEnormaliz` on your instance

**You should see:** A message that the job was scheduled.

**Write down:** Name of the job you ran

### Step 2.9: Learn the manual import way (optional)

*Where:* Your instance

1. Real projects load spreadsheets with Import Sets. To practise once: click **All**, type **Load Data** and open it.
2. Choose **Create table**, label **NSM Users test**, upload **04_users.csv** from **Northstar files**, and click **Submit**.
3. Click **Create transform map**, set the target table to **User [sys_user]**, click **Auto Map Matching Fields**, tick **Coalesce** on user_name, save, and click **Transform**.

**You should see:** The import updates the 60 existing users instead of creating copies. Coalesce does that.

### Checks before you finish the stage

- [ ] The loader result says RESULT: OK.
- [ ] 60 users, 45 laptops and 12 servers exist.
- [ ] NSM-SQL-01 shows CPU count 2 and CPU core count 4.
- [ ] 248 installations, all with a discovery model, in 8 groups.
- [ ] The normalization job ran once.

### If something goes wrong

| Problem | What to do |
| --- | --- |
| The Copy script button does nothing | The guide then opens a box with the script selected: press Ctrl+C (Cmd+C on a Mac). Or download the file on the Scripts page and copy it from there. |

### Step 5.3: Understand the per core rule

*Where:* This guide

1. **Windows Server Standard** is licensed per core. Every physical server needs at least 16 core licenses, and every processor at least 8. Licenses come in packs of 2.
2. Our 4 application servers have 16 cores each: 64. Our 3 SQL servers have only 8 cores each, but the minimum is 16 per server: 48. Together 112. We own 112: **compliant**.
3. **SQL Server Standard** is licensed per core with at least 4 per processor. 3 servers with 2 processors of 4 cores need 24. We own 16: **8 short**. 4 packs at EUR 3,945 make **EUR 15,780** to pay after an audit.
4. Compare this with the Microsoft view and write down what the system shows.

> Without the Microsoft rules a tool counts raw cores: 88 for Windows Server. Per core licensing minimums are why the right answer is 112.

## Glossary

| Term | In plain words |
| --- | --- |
| Allocation | Assigning a license to a specific person or computer. |
| Background script | A page (Scripts - Background) where an admin pastes a script and runs it once. |
| Case study | The final document that tells the project story to managers and interviewers. |
| Content library | ServiceNow's catalogue of known software products, used to recognise and clean names. |
| Content Service | An online service that keeps the content library current on paid instances. A PDI does not have it. |
| Demo data | Sample records ServiceNow can add when you switch on a product. |
| Developer Site | developer.servicenow.com, the website where you get and manage your PDI and switch on paid products for it. |
| Discovery map | The rule that connects found installations to a software model. Without it the model counts nothing. |
| Discovery model | One record for each unique combination of publisher, program name and version found on computers. |
| Entitlement | A record of what was bought: product, how many, license metric, price and dates. |
| Evidence | Screenshots that prove a result. They go in the repository's evidence folder. |
| Import set | ServiceNow's standard way to load a spreadsheet into a table, using a transform map. |
| Installation | A record saying that a program is installed on a computer. Also called a software installation or install. |
| Instance | One company's own copy of ServiceNow, reached at its own web address. |
| License metric | What you count to know how many licenses you need: per user, per device or per processor core. |
| License position | The result of the license check for one product: compliant, under-licensed or over-licensed. |
| Normalization | Cleaning messy software names into one standard name, for example turning 'Microsoft Visio Professional 2021 x64' into Microsoft Visio 2021 Professional. |
| Normalization status | How well a discovery model was cleaned: Normalized, Partially normalized, Publisher normalized, Match not found or Manually normalized. |
| Northstar Manufacturing | Our invented company with 60 employees, 45 laptops and 12 servers. |
| PDI | Personal Developer Instance. A free ServiceNow instance for learning. It is our sandbox. |
| Per core licensing | Paying for each processor core of a server. Microsoft sets minimums per processor and per server. |
| Plugin | A package of features that you switch on in an instance. SAM Professional is a set of plugins. |
| Publisher pack | Extra licensing rules for one vendor, such as Microsoft or Oracle, included in SAM Professional. |
| Reclamation | Taking back licenses that are not used so they can be reused. |
| Reclamation rule | The condition that decides when installed software counts as unused, for example not used for three months. |
| Reconciliation | The license check. It compares what is installed and allocated with what was bought. |
| Release | A ServiceNow version. There are two a year: Zurich (2025), Australia (May 2026) and Brazil (late 2026). |
| Remediation | The options to fix a license problem, such as buying more licenses or removing installations. |
| Removal candidate | An installation the system suggests removing because the reclamation rule found it unused. |
| Role | A set of permissions given to a user, such as sam_admin or sam_user. |
| SAM | Software Asset Management: knowing what software you have and what you may use, and keeping the two in balance at the lowest cost. |
| SAM Professional | ServiceNow's paid SAM product. It cleans software names, calculates license positions and knows the rules of big vendors. |
| Scheduled job | A task the system runs automatically at set times. You can also start one at once with Execute Now. |
| ServiceNow | A cloud platform many companies use to run IT and business processes, such as requests, incidents and assets, in one system. |
| snc_read_only | A platform role that stops a user from creating, changing or deleting anything. |
| Software Asset Workspace | The modern screen in ServiceNow where SAM work is done. |
| Software model | The product as we manage it for licensing, for example Microsoft Visio 2021 Professional. |
| Software usage | Records of when a program was last used and for how long, normally collected by an agent on each computer. |
| Synthetic data | Invented data that looks realistic but describes no real person or company. |
| True-up | Paying the vendor for use above what you bought, often after an audit. |
| Update set | A container that records configuration changes so they can be exported as a backup or moved to another instance. |
